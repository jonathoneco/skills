# Hillclimb

**You own the metric and the experiment's integrity. Supervise and review. Delegate the attempts.** For sustained, iterative improvement of one measurable thing against a target: an eval set's score is one case, CI cost and latency are others. A one-off fix goes to the `diagnosing-bugs` or `perf-issue` skill. This is the loop.

Core discipline: one change, one measurement, keep or revert. Test each change alone before the next goes on top, and claim a win only from a measurement (`principle-prove-it-works`).

**Worth its cost** when one command replays the metric, a replay's cost is known, and, for an eval, the set has known right answers or a blind judge. **Not worth it** when the replay's noise is too large to separate a real gain, such as an eval set with too few rows; then the first job is a bigger eval set or a steadier harness.

Open a todo list before step 1. Its first todo loads the `principle-*` skills the steps name. Then one todo per step, each checked off when its Done when holds, or marked `skip: <reason>`.

1. **Ground the workload and fix the target.** Run the `how` skill over the target, name the realistic workload dimensions that can move the result (data size, history, state, concurrency), and select a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Then fix what is tuned (one prompt, rubric, criteria file, or piece of code), one metric, the direction that counts as better, and a cost per replay. For an eval, freeze its rows by path and commit, and count the metric as rows right out of the total. Set a checkable stop predicate that pairs a target with a floor on attempts, so a lucky early win can't end the run, and a budget in money or replays (the example "at least 50% better than baseline and at least 10 iterations" is this shape). Use the user's numbers when given, otherwise agree them. Done when the target, metric, direction, predicate, and budget are written down.
2. **Build the harness, prove it, freeze it, and measure the noise** (`principle-build-the-lever`). Run contrasting realistic workloads and confirm the target case reproduces the symptom while easier cases separate as expected. If the harness cannot distinguish them, revise the workload or metric. Vet the harness with the `benchmark-checklist` skill before you freeze it, and make it print its error count and a count of the work done. Once frozen, one repeatable command emits the metric. Replay the unchanged baseline at least three times; the noise is the spread between the best and worst baseline score. For a metric made of rows, mark each row **stable** when every run agreed and **swapping** when runs disagreed; a change that only flips swapping rows is noise. When the eval uses a model judge instead of labels, the judge sees outputs blind under sanitized labels, as the `eval` skill says, and its own disagreement is part of the noise. Record a green run of the regression gate (the tests that must keep passing) before any change. Done when the baseline score, the spread, the list of swapping rows, and the green gate run are logged.
3. **Open the decision log** as the `show-me-your-work` skill says. One tab-separated row per attempt: id, hypothesis, change, the score of each run, stable rows fixed, stable rows broken, tests, cost, verdict (kept or reverted), note. Keep it outside the repo's tree, and read it before each attempt. Done when the log file holds this header.
4. **Ground each hypothesis** in the model from step 1, so it names a specific mechanism ("defer X off the boot path because it blocks first paint", "criterion 3 says *statement* where these documents say *summary*"), not "try memoizing something". For an eval, read the rows that are wrong on every run: the input, the expected answer, and what came back. Phrase the change as a general rule; a change that names one document's text is fitted to the eval set, not improved. For a perf or cost metric, order hypotheses by the performance mantras in the `perf-issue` skill, borrowing only their order, not its stop rule. Done when the hypothesis names its mechanism and the rows or cases it should move.
5. **Change and measure, one hypothesis per iteration.**
   - Hand the change to a helper with a tight scope, started as the `scratch-agents` skill says. Supervise and review the diff rather than typing it (`principle-guard-the-context-window`). When several independent hypotheses are live, fan them to parallel helpers, each in its own worktree (`principle-separate-before-serializing-shared-state`).
   - Replay once as a screen: when it scores below the baseline's worst run, or only moves swapping rows, revert it and log why. Otherwise replay until it has as many runs as the baseline, and run the regression gate.
   - Keep it only when the gate stays green, it fixes more stable rows than it breaks, and its mean beats the baseline's mean by at least the spread. Anything less is no gain, including a tweak that "might help": revert it in full.
   - One commit per kept change, staging only the files you changed (`git add <files>`). Log the row either way, kept or reverted.

   Each iteration ends in a check before the next begins (`principle-sequence-verifiable-units`). If the run is unattended, take only the wake mechanism from the harness's loop (in Claude Code, the `loop` skill), not a stop rule; the predicate from step 1 stays the only stop. Done when the change is kept or reverted and logged.
6. **Climb past the plateau, or stop.** Before the next attempt, check the predicate against the log. After three reverts in a row, change the kind of hypothesis (wording, ordering, examples, splitting a criterion, the next mantra), combine near-misses, re-read the wrong rows or the source, or try something more radical before concluding the hill is climbed. Correctness and simplicity outrank the number: revert a win that breaks behavior, and keep a simplification that holds the number (`principle-laziness-protocol`). Stop when the predicate is met with the floor of attempts done, when the budget is spent, or when every hypothesis left touches only swapping rows or is marginal and not worth its cost. Hold the predicate as set, and keep going while cheap untried hypotheses remain. When spending more is a real choice, weigh it as the `weighing` skill says; when you are stuck, surface it instead of spinning. Done when the stop rule is met, or the user has the call with the cost of the next round.
7. **Confirm and report.** Before you report the final number, explain it (`principle-explain-the-number`). Replay the final version and the baseline again, the same number of times, the same day, since a provider can drift between sessions. Report the metric and target, baseline to final with the percent delta and the spread, stable rows fixed and broken, iterations kept and reverted, each kept change in one line, money spent, the log's path, and the best hypothesis worth trying next, graded as the `grading-evidence` skill says. Offer a PR of the kept commits, stacked in the order they landed, as the `opening-a-pr` skill says. Done when every number in the report comes from a run in the log.
